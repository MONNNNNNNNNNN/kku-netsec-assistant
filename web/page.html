Can an attacker steer an AI log analyst?

Attackers control fields that end up in FortiGate logs: User-Agent, URL, DNS query names, login user names. When an LLM reads those logs, that text lands in its prompt. The samples below hide instructions in those fields. They ask the model to call the attack benign and to print CANARY-7731. Select an entry, compare the two prompts, then run the output guard.

Output guard

            
Deterministic code checks every model reply before anyone sees it, and fails closed. Unknown classes and actions become unknown / investigate. A missing verdict becomes unknown / investigate, and duplicates keep the more severe one. An entry the detector flagged can never come back as benign. Independently of the detector, a risk floor from device-generated fields (level, severity, IPS, failed login, external source carrying attacker text) stops the model from clearing an entry: at most it drops to suspicious / monitor. Reasons that repeat attacker text are removed. The reply below is an example model reply, not a live LLM: this page cannot make network requests by design. It plays a manipulated model (log 11 is an attack the detector misses; most entries are missing). Edit it, or paste a real reply. For live triage use the CLI: netsec.js triage.

Deterministic checks decide. The LLM explains.

        
Parsing, rule matching and shadow analysis are ordinary code with unit tests, so every finding cites a config line. The on-prem LLM only gets masked, structured findings. It writes the Thai/English summary and triages logs, and its output passes a guard before a person reviews it. Nothing is changed on any device.

Built for the ISMS from day 1

          
    
            
  • A.8.11 Data masking: IPs, hostnames, e-mails and secrets are replaced with tokens before any LLM call. The mapping stays local.
    • 
            
  • A.5.23 Cloud services: no cloud LLM. The target is a model on the university's own GPU servers.
    • 
            
  • A.5.15 / A.8.2 Access: read-only inputs (backup file, log export). There is no write path to any device.
    • 
            
  • A.8.15 Logging: the CLI appends every LLM call (masked prompt, reply, model, endpoint, timing, SHA-256) to an audit JSONL file with mode 0600.
    • 
            
  • A.8.8 Vulnerabilities: management-plane exposure is flagged with exploited CVEs as context.
    •

Limits of this prototype

          
    
            
  • Static analysis only. A backup has no hit counts, so unused rules are not found yet.
    • 
            
  • Internet-facing interfaces are found by role wan and name. Confirm them.
    • 
            
  • Shadowing skips rules that match on users, groups, ISDB or negation. IPv6 is not analysed.
    • 
            
  • The injection detector is a heuristic: it flags 5/5 of the attacks it was written with but only 1/11 held-out ones (including a payload stitched across two entries). The guard's risk floor, not the detector, is the main control: an experimental mitigation, not yet validated on real traffic or with repeated runs.
    • 
            
  • Config coverage fails closed: parse errors, rules skipped by the shadow analysis (users, groups, ISDB, negate), IPv6 policies and undefined names are listed, and the report is marked INCOMPLETE ANALYSIS (CLI exit 4).
    • 
            
  • The floor only uses device-generated fields. An attack whose device fields look harmless (log 20, a DNS beacon with a reassuring name) can still be cleared by the model. Threat-intel fields (DNS filter category, IOC lists) are the next step.
    • 
            
  • Firmware advisories are not checked offline. Verify on FortiGuard PSIRT.
    • 
          

        

        

          
Run it with a local LLM

          
This page is blocked from network calls, so the LLM steps run from the CLI on a machine that can reach the model server.

          
node cli/netsec.js analyze backup.conf --lang th
node cli/netsec.js narrate backup.conf --lang th \
  --llm http://gpu-host:8000/v1 --model <model>
node cli/netsec.js inject-eval logs.log --ablate --batch 5 \
  --llm http://localhost:11434/v1 --model <model> --runs 3
